# Hoja de Referencia: Cuándo Usar Cada Arquitectura

Un resumen rápido de todo lo visto en el punto 2 (arquitectura a nivel de código/proyecto) y en este punto 11 (arquitectura a nivel de sistema completo), con un ejemplo concreto por cada una — para no tener que releer todos los archivos cuando haga falta decidir rápido.

| Arquitectura | Qué es, en una frase | Cuándo usarla | Ejemplo claro |
|---|---|---|---|
| **[N-Tier (Capas)](../02-calidad-de-codigo-y-arquitectura/08-arquitectura-en-capas-ntier.md)** | Divide el sistema en capas horizontales (Presentación, Negocio, Datos), donde cada capa solo depende de la inmediatamente inferior. | Proyecto chico/mediano, un solo equipo, sin necesidad de escalar partes por separado | Un sistema interno de gestión con un equipo pequeño — como tu propio `OrderManagementBackend` |
| **[Clean Architecture / Hexagonal](../02-calidad-de-codigo-y-arquitectura/09-clean-architecture.md)** | El núcleo de negocio no depende de frameworks ni de infraestructura — todas las dependencias apuntan hacia adentro, hacia las reglas de negocio. | Lógica de negocio compleja que debe sobrevivir cambios de framework o motor de base de datos, o donde la testabilidad es prioridad | Un core de facturación que debe seguir funcionando igual si mañana cambian de SQL Server a PostgreSQL |
| **[CQRS](../02-calidad-de-codigo-y-arquitectura/10-cqrs.md)** | Separa el modelo que escribe (Commands) del modelo que lee (Queries), en vez de una sola clase de servicio que hace ambas cosas. | Lecturas y escrituras con necesidades de rendimiento muy distintas | Un feed tipo Twitter: millones de lecturas por segundo, pocas escrituras — o un dashboard de reportes pesado sobre una base transaccional simple |
| **[Monolito / Monolito Modular](./03-monolitos-y-monolito-modular.md)** | Todo el sistema se compila, despliega y escala como una sola unidad (modular = con límites internos claros entre módulos, aunque siga siendo un solo deployable). | Producto nuevo, equipo chico, dominio de negocio todavía no bien entendido | Una startup validando su MVP — dividir en microservicios ahí de entrada es el error clásico de sobre-ingeniería |
| **[SOA](./04-soa-y-contratos-de-servicio.md)** | Organiza el sistema como servicios que se comunican mediante contratos explícitos y bien definidos (históricamente WSDL/SOAP; hoy, el mismo concepto vía OpenAPI/REST). | Integración entre organizaciones distintas, con contratos formales y estables | Un banco consumiendo el WSDL de su Core Bancario legado (Temenos T24, FIS, FLEXCUBE) |
| **[Arquitectura Orientada a Eventos](./05-arquitectura-orientada-a-eventos.md)** | Un servicio publica un evento sin saber quién lo va a consumir; otros servicios reaccionan de forma desacoplada, sin esperar respuesta. | Varias partes del sistema deben reaccionar a lo mismo sin acoplarse, o hay que absorber picos de carga | Un e-commerce donde "Pedido Creado" dispara en paralelo inventario, facturación y notificaciones, sin que el servicio de pedidos sepa que existen |
| **[Microservicios (por Bounded Context)](./06-microservicios-ventajas-y-costos-ocultos.md)** | El sistema se divide en servicios pequeños, independientes, cada uno con su propia base de datos, desplegables por separado. | Equipos grandes, cada área con lógica de negocio propia e importante, necesidad real de desplegar independiente | Un microservicio por área de negocio (Pedidos, Inventario, Pagos), cada uno con lógica de negocio importante propia |

## Nota honesta sobre documentar todo esto

Elegir la arquitectura correcta es la mitad del trabajo — la otra mitad es dejar registro de por qué se eligió, con ADRs y `ARCHITECTURE.md` (ver [Documentar Decisiones Arquitectónicas](./08-documentar-decisiones-arquitectonicas.md)). Vale la pena leer ahí la nota honesta sobre qué tanto se sostiene esa práctica en equipos reales, antes de asumir que siempre vas a encontrarla bien hecha.
